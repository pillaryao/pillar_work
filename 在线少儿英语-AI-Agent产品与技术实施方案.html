AI transformation blueprint

在线少儿英语
AI Agent 产品与技术实施方案

面向十几人规模团队，以现有 Spring Boot + MySQL 为基础，DeepSeek 主用、OpenAI 备用；先产生业务收益，再按真实调用量升级技术。

适用规模：10–20 人 首期周期：12 周 核心原则：人工确认后执行 文档版本：V1.0

01. 执行摘要

公司当前不需要建设“大而全的 Agent 中台”。首期只做一个嵌入现有系统的 AI 工作台，以及三个能直接影响收入和人效的助手。

3 个首期核心助手：销售、班主任、风险预警
12 周从数据梳理到试点验收
0 次模型直接访问 MySQL 或自动对外承诺
1–3 万元首年新增现金支出参考区间，不含已有人员工资

推荐决策

  1. 项目名称使用“教育业务 AI 提效计划”，不以“多 Agent 平台”为目标。
  2. 第一批只上线“生成建议 + 人工确认”；不自动发送家长消息、不自动改价、不自动退费。
  3. DeepSeek 作为默认文本模型，OpenAI 仅用于备用或少数高难任务；通过统一接口切换。
  4. 复用现有 Spring Boot、MySQL、Redis 和登录权限；首期不引入 Kafka、Kubernetes、Milvus、LangGraph。
  5. 用真实业务指标决定是否继续，而不是以功能数量、模型分数或“是否像人”作为成功标准。
重要校正：“Agent”不等于自主运行的数字员工。对当前规模而言，最合适的产品形态是受控的业务 Copilot：读取被授权的数据、生成结构化建议、由员工确认后写回现有系统。

02. 目标、边界与实施原则

首期业务目标

  • 销售整理线索与生成跟进建议的时间减少 30%。
  • 班主任生成周报、课后反馈的时间减少 50%。
  • 高风险学员在风险出现后 24 小时内进入人工跟进。
  • AI 建议采用率达到 60%，关键事实错误率低于 2%。

首期明确不做

  • 不做实时 AI 外教，不替代教师授课。
  • 不做无人审核的家长沟通与营销群发。
  • 不让模型决定价格、退款、教师处罚或课程承诺。
  • 不做通用多 Agent 自主协作和复杂工作流平台。

六项原则

原则实施要求避免的问题
流程先于模型先画出当前人工步骤、输入、产出与责任人做出“会聊天但不能办事”的功能
结构化输入优先成绩、课时、出勤等由代码查询并传入，不让模型猜数字幻觉和事实错误
默认人工确认发送、写回、创建任务前展示变更内容对客户做出错误承诺
最小数据暴露按角色过滤字段；能用匿名 ID 就不用姓名和电话未成年人信息泄露
可替换模型业务代码只依赖统一 LLM 接口被单一厂商锁定
可测量上线前记录基线，上线后做同口径对比“感觉有用”但无法证明 ROI

03. 部门场景优先级

优先级场景价值风险首期形态
P0销售聊天摘要、字段提取、跟进建议提高跟进量和 CRM 完整度中复制内容或选线索后生成，人工写回
P0班主任课后反馈、学情周报显著减少重复写作中系统数据生成草稿，人工发送
P0规则型流失预警保护续费收入低规则评分 + AI 解释，不用模型直接算概率
P1市场内容改写与多平台适配提升内容产能中品牌模板 + 敏感词检查 + 人工发布
P1经营日报问答减少人工取数中预定义指标查询，不开放任意 SQL
P1教研出题与教案初稿缩短内容制作周期高限定知识点与 CEFR，教研双检
P2外教课后记录总结减少语言与整理成本中基于转写文本生成，抽检音频
暂缓实时课堂提示、全自动排课、多 Agent 协同潜在价值高很高有稳定数据和足够调用量后再评估

优先级由四项共同决定：发生频率、单次耗时、对收入影响、出错后果。不是“模型越炫”越优先。

04. 多阶段实施路线图

阶段 0：基线与数据准备（第 1–2 周）

产出：流程清单、数据字典、20–50 条脱敏评测样本、成功指标基线。

  • 统计销售每条线索整理耗时、班主任每份周报耗时、当前续费与流失口径。
  • 确认学生、家长、线索、课程、订单在系统中的唯一 ID 和关联关系。
  • 制定“允许发送给模型 / 必须脱敏 / 禁止发送”字段清单。

进入下一阶段条件：数据能够通过现有 Service/API 稳定读取，负责人认可验收指标。

阶段 1：AI 基础层 + 销售助手 MVP（第 3–5 周）

产出：模型统一接口、Prompt 版本管理、销售摘要与建议、调用审计。

  • 支持 DeepSeek 主模型与 OpenAI 备用模型；设置超时、重试和每日预算。
  • 销售粘贴聊天记录，系统输出摘要、需求标签、缺失信息、下一步建议和回复草稿。
  • 所有结构化字段通过 JSON Schema 校验；销售点击确认后才写回 CRM。

通过门槛：至少 2 名销售连续试用；字段准确率 ≥ 90%，建议采用率 ≥ 60%。

阶段 2：班主任助手 MVP（第 6–8 周）

产出：课后反馈、周报草稿、可编辑模板、发送前确认。

  • 代码聚合出勤、作业、测评、课堂标签和剩余课时，模型只负责解释和表达。
  • 输出“家长版”和“内部版”，标明每个关键数据的来源时间。
  • 支持重新生成语气，但禁止修改事实数据。

通过门槛：事实错误率 < 2%；单份周报人工耗时下降 ≥ 50%。

阶段 3：流失预警与闭环（第 9–12 周）

产出：可解释风险评分、每日任务、跟进结果记录、经营看板。

  • 首版采用透明规则评分；AI 仅生成原因解释和沟通建议。
  • 每日定时计算风险，不依赖消息队列；高风险自动创建内部待办。
  • 记录“是否跟进、跟进结果、是否续费”，为未来模型训练积累标签。

项目验收：风险召回率和误报率在业务可接受范围；无越权和未审发送事故。

阶段 4：按收益扩展（第 4–6 个月）

仅当前三个场景产生可证明收益后，再依次上线市场内容、经营日报、教研辅助和外教总结。每次只增加一个场景，沿用同一套 AI 基础层。

阶段 5：有限自动化（第 7–12 个月）

只对低风险、可撤销动作开放自动执行，例如内部提醒、日报生成、知识过期提醒。外部发送、资金、合同和学员权益始终保留人工确认。

06. 销售助手 PRD

用户故事

作为销售，我希望系统从家长沟通中提取孩子年龄、基础、目标、预算和顾虑，并给出下一步问题与回复草稿，以便更快完成高质量跟进。

输入与输出

类型内容规则
输入聊天文本、线索来源、历史跟进、课程目录手机号、微信号等先脱敏；课程价格由系统提供
输出摘要、需求标签、意向等级、缺失信息、下一步动作JSON Schema 校验，枚举字段不允许自由生成
文案回复草稿、异议处理话术不得承诺折扣、效果、名额和退款政策
动作更新 CRM 草稿、创建跟进任务展示 diff，销售确认后执行

推荐输出结构

{
  "summary": "家长为 8 岁孩子咨询口语提升课程",
  "needs": ["口语", "自信表达"],
  "knownFacts": {"age": 8, "budget": null, "level": "基础一般"},
  "missingQuestions": ["每周可上课时间？", "是否参加过系统测评？"],
  "intentLevel": "B",
  "nextAction": {"type": "INVITE_ASSESSMENT", "dueInHours": 24},
  "replyDraft": "建议先安排一次水平测评……",
  "warnings": ["预算尚未确认"]
}

验收标准

  • 同一条聊天记录不会把未知预算或年龄补成确定数字。
  • 课程名称、价格和权益只能来自系统提供的候选列表。
  • 保存前用户能看到将新增或修改的 CRM 字段。
  • 模型超时或 JSON 不合法时，原 CRM 数据不发生变化。
  • 每次生成均记录模型、Prompt 版本、操作者和是否采用。

07. 班主任助手 PRD

核心任务

课后反馈

基于单节课堂结构化标签和教师评语，生成简洁、积极但不夸大的家长反馈。

学情周报

聚合一周出勤、作业、测评和知识点表现，给出可执行的家庭练习建议。

续费准备

汇总学习进步、剩余课时和历史诉求，生成内部沟通提纲，不自动催费。

事实与表达分离

由代码确定，不交给模型计算允许模型生成
课程次数、出勤率、作业完成率、分数、剩余课时趋势解释、亮点总结、建议的自然语言表达
知识点名称、课堂标签、教师原始备注按家长阅读习惯组织段落与语气
是否达到预警阈值对风险原因做清晰说明

家长版模板

  1. 本周概览：只陈述已验证的数据。
  2. 本周亮点：最多两项，引用课堂标签或教师备注。
  3. 需要巩固：避免给孩子贴负面标签。
  4. 家庭建议：最多两项，每项 5–10 分钟、可以执行。
  5. 下周目标：与课程计划一致，不额外承诺教学效果。
红线：禁止生成医疗、心理诊断；禁止使用“智力差、懒惰”等标签；禁止夸大学习效果；模型不得擅自改变教师原始评价中的事实。

08. 学员风险预警 PRD

十几人团队不应先训练预测模型。首版采用可解释、可调整的业务规则，AI 负责解释和建议，避免把模型幻觉包装成“89% 流失概率”。

示例评分规则（需用历史数据校准）

信号条件示例分值说明
近期缺课14 天内缺课 ≥ 2 次+25排除已登记长期请假
作业下降近 4 次完成率 < 50%+20需有至少 3 次作业样本
家长负面反馈投诉或明确表达不满意+30人工标记，保留原始依据
长时间无互动连续 14 天无有效学习行为+20假期或停课状态不计
临近课耗尽剩余课时 ≤ 10 且未有续费计划+15属于续费提醒，不等同于不满

等级：0–29 低风险；30–59 中风险；60–100 高风险。分值是排序工具，不宣称统计概率。

关键架构决定

决定首期方案原因
部署方式现有 Spring Boot 内新增独立模块团队小、调用量低，减少网络和运维复杂度
Agent 编排显式 Java 工作流 / 状态枚举流程短且固定，可调试、可审计

核心接口

public interface LlmGateway {
    <T> LlmResult<T> generate(
        TaskType taskType,
        PromptInput input,
        Class<T> outputType,
        LlmOptions options
    );
}

public interface AssistantWorkflow<C, R> {
    R prepare(C context);      // 查询并冻结事实数据
    R generate(C context);     // 调用模型并校验输出

}
实现建议：若团队熟悉 Spring AI，可用它处理模型客户端和结构化输出；工作流、审批、权限和审计仍由自己的 Java 代码控制。不要让框架成为业务规则的唯一载体。

12. 模型接入、路由与成本控制

供应商策略

  • 默认：DeepSeek，用于摘要、分类、普通文案和结构化提取。
  • 备用：OpenAI，仅用于 DeepSeek 服务异常，或评测证明特定复杂任务质量显著更高时。
  • 模型配置化：模型名、温度、最大输出、超时、单价均保存在配置中，不写死业务代码。

路由与容错

请求 → 权限检查 → 输入脱敏 → 预算检查 → 主模型
                                         ├─ 成功且结构合法 → 保存结果
                                         ├─ 限流/5xx → 退避后重试 1 次
                                         └─ 仍失败 → 按任务配置切备用模型

注意：内容不安全、输入过长、JSON 校验失败不应无限重试。

成本公式

单次成本 = 输入 Token ÷ 1,000,000 × 输入单价 + 输出 Token ÷ 1,000,000 × 输出单价

价格会变化，不能在代码中固定金额。管理员按供应商账单更新单价；系统按天、部门、任务和模型统计成本。

控制项建议初值处置
单次输入上限按任务设置；聊天只取相关窗口超限先代码摘要或要求缩小范围
用户每日限额根据岗位试点量配置达到 80% 提示，100% 阻断非关键任务
公司月度预算先以小额试点额度运行70% / 90% 告警；备用模型不自动突破总预算
缓存只缓存不含动态隐私的模板或知识检索家长聊天和学情结果默认不做共享缓存

状态约束

DRAFT → GENERATING → GENERATED → APPROVED → EXECUTED；失败进入 FAILED，用户取消进入 CANCELLED。只有 APPROVED 状态允许执行写操作，且执行接口必须幂等。

保留策略：调用元数据可长期保留用于审计；包含家长聊天、课堂内容和学情详情的 payload 应按业务和法律要求设置最短必要期限，并支持删除请求。具体期限需由公司法务/隐私负责人确认。

14. API 与受控工具设计

方法与路径说明权限/安全
POST /api/ai/sales-analysis生成销售分析，不写 CRM线索归属校验、输入脱敏
POST /api/ai/student-reports按学员和日期生成报告班主任归属校验
GET /api/ai/runs/{id}查询运行结果和待确认动作创建人或授权管理者
POST /api/ai/runs/{id}/approve确认待执行内容二次校验对象权限
POST /api/ai/runs/{id}/execute幂等写回 CRM/创建内部任务只接受已确认 payload
POST /api/ai/runs/{id}/feedback记录采用、修改和错误分类操作者本人
GET /api/ai/admin/usage查看用量、成本和错误率管理员，仅汇总数据

“工具调用”的正确边界

首期不必建设 MCP 平台。将能力实现为 Java Tool/业务 Service 即可：

StudentSnapshot getStudentSnapshot(studentId, operator)
CourseCatalog getAllowedCourseCatalog(operator)
DraftId createCrmDraft(leadId, proposedChanges, idempotencyKey)
TaskId createInternalFollowup(ownerId, reason, dueAt, idempotencyKey)
  • 查询工具返回最小只读 DTO，不返回整个数据库实体。
  • 写工具永远不由模型直接调用；模型只提出 PendingAction。
  • 服务端重新验证操作者权限，不信任前端传入的 ownerId。
  • 所有写操作必须有幂等键，防止超时重试造成重复任务。

15. Prompt、结构化输出与轻量知识库

Prompt 四层结构

  1. 系统规则：角色、禁止事项、必须基于事实、未知值处理。
  2. 任务说明：本次任务目标、输出语言和语气。
  3. 受信数据：代码查询的事实和审核过的知识，以明确分隔符包裹。
  4. 输出 Schema：字段、类型、枚举、长度和必填规则。
防 Prompt 注入：家长聊天、教师备注和知识文档都属于“不可信数据”。即便文本中写着“忽略之前规则”，也只能作为被分析内容，不能改变系统指令或触发工具。

知识库演进

阶段方案适用条件
首期MySQL 管理课程、FAQ、话术和模板；按标签/关键词筛选后放入 Prompt文档少、结构明确、更新人有限
扩展复用现有 Elasticsearch 做全文检索数千篇资料且已有 ES 运维能力
再升级Embedding + 向量检索 + rerank全文检索召回不足，且评测证明 RAG 有增益

每条知识必须有负责人、适用部门、有效期、版本和审核状态。过期或未审核内容不得进入生产 Prompt。

16. 权限、未成年人隐私与内容安全

数据分级建议

级别示例模型使用策略
公开公开课程介绍、品牌文案可使用
内部SOP、销售话术、内部指标按岗位授权，禁止进入公开模型训练
敏感孩子姓名、声音、课堂视频、成绩、家长联系方式最小化、脱敏、明确目的和期限
严格限制支付信息、证件、健康与特殊情况默认禁止发送给第三方模型

上线前必须完成

  • 与模型供应商确认数据保留、训练使用、处理地域和删除机制，并签署所需协议。
  • 在隐私政策或授权流程中明确课堂音视频、转写和 AI 分析用途。
  • 建立字段级脱敏：电话、微信号、地址、证件等不进入 Prompt。
  • 沿用现有 RBAC，并增加对象归属校验；仅有菜单权限不足以保护具体学员。
  • 记录读取、生成、审批、写回、导出和删除审计日志。
  • 配置输出内容过滤，并为敏感任务设置人工复核。

本节是产品与技术控制建议，不构成法律意见。上线前应结合实际经营地、服务对象所在地及供应商条款完成法律评估。

17. 评测、灰度与验收

离线评测集

每个核心任务准备 20–50 条脱敏真实样本，覆盖正常、缺失、矛盾、超长、敏感、恶意指令六类。每次修改 Prompt 或模型后自动回归。

维度测量方式首期参考门槛
结构合法率JSON Schema 自动校验≥ 99%
字段提取准确率与人工金标准对比≥ 90%
事实错误率报告中错误事实数 / 事实总数< 2%
安全通过率敏感信息、越权、注入测试100% 阻断高危用例
采用率被采用结果 / 已生成结果≥ 60%
效率提升上线前后同类任务中位耗时销售 ≥ 30%，班主任 ≥ 50%

灰度顺序

  1. 开发人员使用模拟/脱敏数据验证。
  2. 每个岗位选择 1 名种子用户，只生成不写回。
  3. 扩至 2–3 名用户，开放人工确认后写回。
  4. 观察两周指标与事故记录后再全员开放。

评测门槛必须按业务风险调整。例如市场创意可接受较多修改，学情数字则必须接近零错误。

18. 日志、监控、降级与运维

最小监控集

  • 调用成功率、P50/P95 延迟、超时率
  • 结构校验失败率、敏感内容拦截率
  • 按任务/部门/模型统计 Token 与估算成本
  • 采用率、修改率、错误反馈分类
  • 待审批积压、写回失败和重复执行

降级策略

  • 模型不可用：保留人工原流程，不阻断核心业务。
  • 备用模型也失败：保存任务并提示稍后重试。
  • 输出不合法：最多修复一次，之后交人工。
  • 预算超限：暂停市场批量生成等非关键任务。
  • 发现数据泄露风险：一键关闭对应 Agent。

定时任务可靠性

使用数据库任务表记录 PENDING/RUNNING/SUCCESS/FAILED，配合 Spring Scheduler 拉取；任务有租约、最大重试次数和幂等键。对于当前规模，这比引入 Kafka 更简单且足够可靠。

19. ROI、预算与经营指标

收益计算

月度节省人时 = 月任务量 ×（原平均耗时 - AI 后平均耗时）÷ 60
人效价值     = 月度节省人时 × 对应岗位小时成本
收入增益     =（试点后转化/续费 - 基线）× 有效客户量 × 客单贡献
净收益       = 人效价值 + 收入增益 - API - 新增云资源 - 外部采购
ROI          = 净收益 ÷ 项目投入

转化率和续费率受季节、渠道和课程变化影响，最好使用同期对照组，不要把全部增长归因于 AI。

首年新增现金预算参考

项目参考范围控制方式
模型 API先设置 300–1,000 元/月预算；按真实量调整限额、短上下文、小模型优先
云资源原则上复用现有资源不新增向量集群、消息队列和 K8s
文件/日志存储少量对象存储和备份费用生命周期自动清理敏感 payload
外部服务按需：语音转写、内容审核先按量，不签大额年框
内部研发主要投入项，使用现有团队一次只交付一个场景
预算说明：“首年 1–3 万元”只适用于复用现有研发和基础设施的新增现金支出估计，不应当被理解为项目总成本。管理决策时必须计入内部研发机会成本。

21. 主要风险与技术升级阈值

风险早期信号应对措施
功能没人用采用率低、员工仍复制到公共 ChatGPT嵌入原流程，减少输入，针对拒绝原因迭代
事实错误数字、价格、课程权益被改写事实由代码提供和锁定，Schema 校验，人工确认
数据泄露Prompt 中出现电话、地址或无权限学员字段级脱敏、对象级鉴权、供应商配置和审计
成本失控长聊天反复提交、备用模型频繁触发上下文裁剪、预算限额、路由告警
复杂度过早大量时间用于基础设施而非试点维持单体模块和显式工作流，以指标触发升级

何时才升级

技术不要因为建议触发条件
独立 AI 微服务“听起来更企业级”发布节奏或资源隔离已经影响主系统，或多应用复用
向量数据库资料可以上传全文检索评测召回不足，向量方案有可测增益
Kafka存在定时任务数据库任务表成为可靠性/吞吐瓶颈且有运维能力
LangGraph/复杂编排Agent 数量增加出现长流程、分支、暂停恢复，显式代码维护成本明显上升
MCP行业流行工具需被多个不同 Agent 客户端标准化复用
自训练风险模型想显示“流失概率”积累足量、高质量、无泄漏的历史结果标签并能持续监控漂移

22. 立即启动清单

本周管理动作

  1. 指定一位对业务结果负责的项目 Owner。
  2. 选择 1 名销售、1 名班主任作为种子用户。
  3. 记录两类工作各 20 次的真实耗时，形成基线。
  4. 准备 20–50 条脱敏样本，并给出人工标准答案。
  5. 梳理模型供应商条款和未成年人数据授权。

首个 Sprint 的完成定义

  • 可以通过配置切换 DeepSeek/OpenAI，密钥不进入代码库。
  • 输入在发送前完成脱敏，调用有操作者和业务对象审计。
  • 销售分析返回严格 JSON，并通过后端 Schema 校验。
  • 界面清楚区分“AI 建议”和“已确认业务事实”。
  • 失败时不修改现有数据，并允许员工继续原人工流程。
最终建议：先把销售助手做成真正每天有人使用的工具，再复制同一底座到班主任场景。只有业务闭环跑通后，才把它称为 Agent；否则它只是一个生成文本的入口。
